# PR1 AutoEatSleep native integration cases

These are test-only runtime-test-v2 smoke-suite cases. The game operator owns deployment, CWL execution, the result manifest, and save reload. Compile/generation alone is not a runtime pass.

| Case ID (`pr1.autoeat.` prefix) | Actual operation and assertions |
| --- | --- |
| `config_default_preserved` | Real loaded ModConfig + BepInEx ConfigFile: absent key gives Hungry=3; saved explicit 1 remains 1 and file bytes remain unchanged. |
| `reentry_consumption` | Native hunger.Mod crosses the Hungry boundary, reaching the installed Stats.OnChangePhase postfix, InstantEat and FoodEffect.Proc. Each of two outer triggers consumes one unit, changes nutrition/hunger, observes a native nested phase, and never exceeds depth 1. |
| `filters_threshold` | Below threshold, disabled, AI_Eat, important food, native-rejected rotten food, and food in an excluded container produce zero calls/consumption. A matching container provides one meal. |

## Fixture contract

- Both the shared runner and the local fixture require the original PC name to contain `RUNTIME_TEST`; an active loaded plugin/map/renderer and its installed postfixes are mandatory. Missing prerequisites fail instead of passing.
- Use a backed-up, disposable dedicated save/zone. Run one CaseId at a time; stop and reload on failed restoration or cleanup. A sticky local guard rejects subsequent cases in the same compiled script after a restore/cleanup failure; use a fresh script/session after reloading. Do not run alongside another suite, save/load, world transition, or pending next-frame initialization.
- The fixture creates a non-global Chara, a small native prepared-food stack, an important-food control, and (when needed) a container. Source-created inventory and meal effect traits are controlled only on newly created fixtures. No preexisting item is moved/deleted.
- Container selection scans the actual loaded things rows in ordinal ID order for the ordinary native TraitContainer token, derived from its type name using Card.ApplyTrait's `Trait` prefix rule. Both cards/things maps must contain the source ID. Native generation must produce the exact trait, an owned inventory and positive native width/height/capacity. Native Prespawn contents are recorded at the factory boundary by Own and removed only through the existing ownership gate, leaving an empty controlled box. The chosen ID, source trait parameters, native type/dimensions/capacity and removed fixture-content count are logged. No English label/guessed source ID is used. Existing unmatched/matched filter and quantity assertions remain unchanged. The installed DLL establishes this selection rule, but the concrete selected loaded-source ID and filter pass still require operator execution; a read-only catalog probe is provided in the review artifacts.
- Setup disables auto-sleep in a separate ConfigFile with SaveOnConfigSet=false. Product MyConfig is replaced only during the synchronous operation; the original live settings and saved cfg bytes are checked. Existing saved thresholds are never forced to 3.
- Each operation temporarily uses a new Player pointing at the dedicated fixture Chara. Its queues, notices, stats, disease, nutrition and AI do not belong to the original Player. Native AddCondition is performed while the fixture is NPC, avoiding PC EndTurn during preparation. No frames or child IEnumerator are yielded while the Player/config references are replaced.
- The fixture-only Party uses native SetLeader, setting uidLeader and RefChara's cached reference, plus matching member-reference and member-UID lists. It remains non-global: SetLeader has no global registration, and RefChara.GetAndCache can resolve the living actor on the current map. Activation independently logs/asserts native IsPC, EClass.pc identity, leader identity, IsPCParty, and hunger TrackPhaseChange. The previous members-only setup left uidLeader=0, blocking six runtime cases before their functional operations; the original combined PC/leader assertion is retained.
- After the party correction passed in-game, the first native CanEat call failed in ElementContainer.Value at IL_003f. CharaGen.Create had initialized NPC elements/body/stats, but left faction unset. Once the actor became PC, its own null faction compared equal to pc.faction, entering PC-faction fallback and dereferencing pc.faction.charaElements. This is a test-fixture blocker, not a product failure.
- Pr1NativePcContext creates an independent FactionManager through the game's OnCreateGame -> Faction.Create -> Init -> AssignUID path, then assigns its native Home using Chara.SetFaction. No original faction object/dictionary is edited. FactionManager is switched only inside synchronous preparation/activation and restored in finally; the original Game/Player/PC/party/global assertions remain. Actor stays non-global. Player uses the real constructor and an owned Chara; full Player.OnCreateGame is intentionally not invoked because it creates extra actors, loads PCC files and modifies Game.config.
- The common native preflight checks faction lookup, source/race/job/biography, element/body/renderer ownership, Player containers, condition ownership, stat sources and native absent/present-element evaluation. FoodEffect/ProcNutrition/ProcTrait, Vomit/ModExp/ModWeight and Condition.Kill/ConSleep.OnRemoved were inspected against the actual installed DLL. Newly generated actor faith is set through native SetFaith to Eyth, as in new-PC initialization. Seed-spawning, rotten-edible and machine-food actors fail fixture preparation; food is the exact native TraitFoodPrepared type, excluding achievement food IDs and subclasses with unrelated side effects. Sleep removal rejects slept/PC-tick/mount/pickup paths. Native behavior is neither replaced nor stubbed, and the existing functional assertions are unchanged.
- Baseline snapshots additionally assert original Game/Player/PC/party/map/card-manager/global/carryover references, original leader, ordered party references/UIDs and carryover contents, and every existing global UID's exact Chara reference. finally restores the captured Game and Player roots; no original party or global entry is edited or replaced to activate the fixture.
- Original FactionManager, dictionary/role/faction references, relation owner/type/affinity, both element-container dictionaries, exact Element/owner references and all eight raw integer fields are also checked after activation and cleanup. Baseline native faction getters resolve PC/map/global/carryover/party Chara caches under the original manager, then check their faction IDs and exact references after restoration. SetFaith runs after the preparation manager switch has been restored. The fixture faction has no retained registration in the original manager.
- finally restores Player, config, saved AI, the captured eating-guard value, Act.CC/TC/TP, shared Stats raw bindings and BaseStats.CC. Guard restoration happens only after the case's normal retry/assertions, so a stuck guard still fails the exception case. Assertions compare original PC stats, elements, conditions, inventory roots/parents/slots/quantities, party/carryover/global UIDs, other map Chara HP/stats/position/conditions/inventory, existing map items, world date and live config bytes. Phase observers read Stats.Hunger and BaseStats.CC directly rather than rebinding shared stats through a Chara getter.
- Rollback is registered before fixture creation. At known creation boundaries, the destruction gate records every descendant UID, exact reference, and parent; original map/global/carryover/inventory UIDs cannot be adopted. Explicit native fixture moves update only known records. Cleanup validates the complete graph before any destruction and again immediately before each Destroy. An unknown child, replaced reference/UID, or unexpected owner leaves cards intact and fails cleanup. It never adopts cards discovered at the end of a run. Configuration/static restoration and observer removal continue after cleanup failures. Condition.Kill requires the exact recorded ConSleep with fixture owner. Vomit ownership requires a fresh unparented Thing ID 731 passed by this fixture's native Vomit and then inserted into the current map.
- Runtime logs include fixture/food/container UIDs, quantities, roots, native invocation counts, nested phases, injection counts, restoration and cleanup results. Preserve the result JSON and Player.log plus game/build and loaded DLL hashes in the operator manifest.

## Offline verification

`Pr1NativePrerequisiteProbe` runs before activation/readiness assertions and functional calls in every existing native case. One `native-prereq:data:` JSON dictionary retains every named diagnostic, followed by one `native-prereq:complete` line. This leaves room for both full diagnostics and restoration/cleanup under the unmodified context/host 64-log caps, including cases with two activations. Fields report source/race/job, exact owner/reference comparisons, renderer, map/global membership, party/faction, raw elements, Player containers, food and sleep/condition/stat prerequisites. Each getter is isolated: null is `<null>`, exceptions retain type/message, and other reads continue. It does not invoke CanEat/Evalue/InstantEat/FoodEffect/Vomit/Condition.Kill, create conditions, or change fixture initialization. Getter errors stop before functional operations; functional assertions and finally/cleanup remain unchanged. Run `pr1.autoeat.reentry_consumption` once via the sole operator; preserve the data/complete and cleanup/rollback records. No new case ID is introduced.

The one-run probe confirmed `actor.rawSlots=null` while actor source/body/renderer owners, map and party were valid. Native IL shows rawSlots is a serialized body-slot snapshot: only Chara.OnSerializing writes it from body.slots; CharaBody.get_rawSlots reads it, and SetOwner's deserialization branch explicitly accepts null. New NPC runtime body slots are independent of this saved array. There is no runtime rawSlots getter to initialize for eating, and CanEat/FoodEffect/Vomit/sleep removal do not directly reference it. Accordingly only the artificial rawSlots non-null readiness operand was removed. rawSlots remains in diagnostics; no fake array, manual serialization or new fixture initialization is introduced. This does not establish a native functional runtime pass.

## Coverage limits and candidates

- All game cases still require actual CWL compilation/execution and runtime cleanup evidence. Static native-reference compilation does not validate Harmony patch installation/injection order or active scene behavior.
- Sleep exercises real condition removal with `slept=false`, avoiding dream/recipe/night advancement. Completed overnight sleep, hot-item input, AutoAct child restoration and visible UI progression remain separate unexecuted checks.
- The current product searches loose root food even when UseContainerFilter=true; the excluded-container case covers unmatched nested containers. The config description says "Only search for food in specific containers", so loose root food is a specification/defect candidate to clarify, not a silently changed product expectation.
- Fixture generation advances native UID/RNG counters. Do not rewind UID allocation. Reload the disposable save after the suite to discard these and any scene/UI/native side effects beyond the explicit state assertions.
